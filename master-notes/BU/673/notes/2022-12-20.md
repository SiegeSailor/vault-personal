## Basic SE Concepts

### 1. Explain essential difficulties and accidental difficulties described by Brooks in the paper “No Silver Bullet”.

In his paper "No Silver Bullet," Fred Brooks distinguishes between two types of difficulties that software developers face: essential difficulties and accidental difficulties.

Essential difficulties are inherent to the nature of the problem being solved and cannot be eliminated through the use of technology or other means. For example, developing a software program that can accurately translate spoken language into written text is an essential difficulty because it requires the program to understand and interpret the nuances and complexities of human language.

Accidental difficulties, on the other hand, are not inherent to the problem itself, but rather arise from the way in which the problem is being addressed. These difficulties can often be reduced or eliminated through the use of better tools, methodologies, or technologies. For example, debugging a software program can be an accidental difficulty if the program is poorly designed or if the developer does not have access to good debugging tools.

In his paper, Brooks argues that while there have been significant advances in software development tools and technologies over the years, the essential difficulties of software development remain largely unchanged. As a result, he concludes that there is no "silver bullet" that can significantly reduce the complexity and effort required to develop software.

### 2. Describe the software engineering code of ethics.

- **PUBLIC** – Software engineers shall act consistently in the public interest.
- **CLIENT** AND EMPLOYER – Software engineers shall act in a manner that is in the best interests of their client and employer and consistent with the public interest.
- **PRODUCT** – Software engineers shall ensure that their products and related modifications meet the highest professional standards possible.
- **JUDGMENT** – Software engineers shall maintain integrity and independence in their professional judgment.
- **MANAGEMENT** – Software engineering managers and leaders shall subscribe to and promote an ethical approach to the management of software development and maintenance.
- **PROFESSION** – Software engineers shall advance the integrity and reputation of the profession consistent with the public interest.
- **COLLEAGUES** – Software engineers shall be fair to and supportive of their colleagues.
- **SELF** – Software engineers shall participate in lifelong learning regarding the practice of their profession and shall promote an ethical approach to the practice of the profession.

### 3. Compare the waterfall model, spiral model, unified process model, and agile model. How can these models apply to contemporary development?

The waterfall model, spiral model, unified process model, and agile model are all software development methodologies that are used to plan, design, and build software systems.

The waterfall model is a linear, sequential approach to software development in which each phase of the development process is completed before the next phase begins. This model is characterized by strict planning and control, with little room for change or iteration.

The spiral model is a risk-driven approach to software development that involves iteratively building and testing prototypes of a system. This model is useful for projects that involve a high level of uncertainty or risk, as it allows for flexibility and the incorporation of feedback from stakeholders.

The unified process model is an iterative and incremental approach to software development that combines elements of both the waterfall model and the spiral model. This model is characterized by a focus on risk management and the use of an iterative, incremental approach to development.

The agile model is a flexible, adaptive approach to software development that emphasizes rapid delivery, continuous iteration, and the ability to respond to changing requirements. Agile methodologies are based on the Agile Manifesto, which outlines principles such as individuals and interactions over processes and tools, and working software over comprehensive documentation.

All of these models can be applied to contemporary software development, and the choice of which model to use will depend on the specific needs and constraints of the project. Some projects may be more suited to a more structured, linear approach like the waterfall model, while others may benefit from a more flexible and adaptive approach like the agile model.

### 5. Describe what CMMI is.

CMMI (Capability Maturity Model Integration) is a process improvement model that provides organizations with a framework for improving their software development and maintenance processes. CMMI was developed by the Software Engineering Institute (SEI) at Carnegie Mellon University, and is used by organizations around the world to improve the quality and effectiveness of their software development processes.

CMMI is based on the idea that an organization's software development processes can be evaluated and improved in a systematic manner. It consists of a series of levels of process maturity, ranging from Initial (the lowest level) to Optimizing (the highest level). Each level represents an increase in the maturity and effectiveness of an organization's processes, and organizations can use CMMI to assess their current level of process maturity and identify areas for improvement.

CMMI is used in a variety of settings, including software development, manufacturing, healthcare, and government. It is designed to be flexible and adaptable, and can be customized to meet the specific needs of an organization. By using CMMI, organizations can improve the efficiency, effectiveness, and reliability of their software development processes, and deliver high-quality software products to their customers.

### 6. Describe the Agile manifesto and principles.

The Agile Manifesto is a set of guiding values and principles for software development that was first published in 2001. The Agile Manifesto was developed by a group of software development practitioners who were seeking a more flexible and adaptive approach to software development than was offered by traditional methods such as the waterfall model.

The Agile Manifesto consists of four values and twelve principles. The values of the Agile Manifesto are:

Individuals and interactions over processes and tools
Working software over comprehensive documentation
Customer collaboration over contract negotiation
Responding to change over following a plan
The principles of the Agile Manifesto are:

Our highest priority is to satisfy the customer through early and continuous delivery of valuable software.
Welcome changing requirements, even late in development. Agile processes harness change for the customer's competitive advantage.
Deliver working software frequently, from a couple of weeks to a couple of months, with a preference to the shorter timescale.
Business people and developers must work together daily throughout the project.
Build projects around motivated individuals. Give them the environment and support they need, and trust them to get the job done.
The most efficient and effective method of conveying information to and within a development team is face-to-face conversation.
Working software is the primary measure of progress.
Agile processes promote sustainable development. The sponsors, developers, and users should be able to maintain a constant pace indefinitely.
Continuous attention to technical excellence and good design enhances agility.
Simplicity--the art of maximizing the amount of work not done--is essential.
The best architectures, requirements, and designs emerge from self-organizing teams.
At regular intervals, the team reflects on how to become more effective, then tunes and adjusts its behavior accordingly.
The Agile Manifesto and principles have been influential in the software development community and have led to the development of a number of agile methodologies, including Scrum, Extreme Programming (XP), and Lean Software Development. Agile methodologies are based on the idea of rapid iteration and continuous delivery, and are designed to be flexible and adaptable to changing requirements. They are particularly well-suited to projects that involve a high degree of uncertainty or complexity.

### 7. Compare XP and Scrum. Explain basic practices and terms in each framework, such as user stories, pair programming, TDD, sprint, scrum master, etc.

XP (Extreme Programming) and Scrum are both agile software development methodologies that are based on the principles of the Agile Manifesto. Both XP and Scrum prioritize rapid delivery, continuous iteration, and the ability to respond to changing requirements. However, there are some key differences between the two frameworks:

XP:

XP is a comprehensive software development methodology that includes a set of practices and values that aim to improve the quality and speed of software development.
Key practices in XP include:
Pair programming: Two programmers work together at one computer, with one programmer writing code and the other reviewing and providing feedback. This helps to improve code quality and facilitate knowledge sharing.
Test-driven development (TDD): Developers write automated tests for their code before they write the code itself. This helps to ensure that the code meets the desired specifications and reduces the risk of defects.
Continuous integration: Developers integrate their code into a shared repository frequently, typically multiple times per day. This helps to identify and fix problems early in the development process.
Refactoring: The process of improving the design of existing code without changing its functionality. This helps to keep code maintainable and easy to understand.
XP values collaboration, simplicity, and feedback.
Scrum:

Scrum is a framework for managing and completing complex projects. It is based on the idea of "sprints," which are short, iterative cycles of work that focus on delivering a specific piece of functionality.
Key practices in Scrum include:
User stories: Short descriptions of the desired functionality from the perspective of the user. User stories are used to define and prioritize work in a sprint.
Sprint planning: A meeting at the beginning of a sprint in which the team determines what work will be completed during the sprint.
Daily stand-up: A short meeting held every day in which team members discuss their progress, any obstacles they are facing, and what they will work on next.
Sprint review: A meeting at the end of a sprint in which the team demonstrates the work completed during the sprint to stakeholders and discusses any lessons learned.
Sprint retrospective: A meeting at the end of a sprint in which the team reflects on the sprint and identifies ways to improve the process in the future.
Scrum master: The person responsible for facilitating the Scrum process and helping the team to follow the Scrum framework.
Overall, both XP and Scrum are designed to promote rapid delivery, continuous iteration, and the ability to respond to changing requirements. They both place a strong emphasis on collaboration, simplicity, and feedback, and are well-suited to projects that involve a high degree of uncertainty or complexity.

### 8. Describe key features of DevOps.

Monitoring and feedback: DevOps emphasizes the importance of monitoring the performance and reliability of software systems, and using this information to identify and address problems in a timely manner. Lean principles: DevOps is inspired by lean manufacturing principles, which emphasize the importance of continuous improvement, waste reduction, and customer focus. DevOps aims to apply these principles to software development and operations, with the goal of increasing efficiency and delivering value to customers.

By embracing these principles, organizations can adopt a DevOps culture and approach to software development and operations, which can help them to deliver high-quality software more quickly and reliably.

### 9. Describe quality metrics (including process and product metrics) and their indications. List quality metrics used in your project and explain how to interpret these metrics and how to improve the quality.

Quality metrics are measures of the quality of a software system or process. Quality metrics can be classified into two categories: process metrics and product metrics.

Process metrics measure the effectiveness and efficiency of a software development process. Some examples of process metrics include:

Lead time: The time it takes to complete a software development project from start to finish.
Cycle time: The time it takes to complete a specific task or activity within a software development project.
Defect density: The number of defects per unit of code.
Code review efficiency: The percentage of code that is reviewed and the amount of time it takes to review code.
Product metrics measure the quality and performance of a software product. Some examples of product metrics include:

Usability: The ease with which a user can learn and use a software system.
Reliability: The ability of a software system to perform its intended functions consistently over time.
Performance: The speed and efficiency with which a software system performs its intended functions.
Security: The ability of a software system to protect against unauthorized access or attacks.
To improve the quality of a software system or process, it is important to regularly measure and track quality metrics and use this information to identify areas for improvement. For example, if a software system has a high defect density, this could be an indication that the development process needs to be improved, such as by incorporating more thorough testing or code reviews. Similarly, if a software system has poor usability, this could be an indication that more user testing and user interface design is needed. By regularly measuring and tracking quality metrics, organizations can identify areas for improvement and take action to address them.

### 10. Compare validation and verification in the quality assurance process. Explain code review, inspection, and testing.

Validation and verification are two important activities in the quality assurance (QA) process.

Validation is the process of evaluating a system or component during or at the end of the development process to determine whether it satisfies the specified requirements. Validation is concerned with evaluating whether a system will meet the needs of the users and stakeholders, and is typically performed using techniques such as user acceptance testing and functional testing.

Verification is the process of evaluating a system or component during or at the end of the development process to determine whether it meets the specified requirements. Verification is concerned with evaluating whether a system has been designed and implemented correctly, and is typically performed using techniques such as code review, inspection, and testing.

Code review is the process of reviewing source code in order to identify defects, improve code quality, and ensure that the code adheres to coding standards and best practices. Code review can be performed manually, or with the use of automated tools such as static analysis tools.

Inspection is a formal, systematic process for reviewing a system or component in order to identify defects and improve quality. Inspections typically involve a team of reviewers who analyze a system or component using a structured process, and identify defects and areas for improvement.

Testing is the process of evaluating a system or component to determine whether it satisfies specified requirements and to identify defects. Testing can be performed at various stages of the development process, and can involve a variety of techniques such as unit testing, integration testing, and acceptance testing.

In summary, validation and verification are two important activities in the QA process that are used to ensure that a system or component meets the specified requirements. Validation focuses on evaluating whether a system will meet the needs of users and stakeholders, while verification focuses on evaluating whether a system has been designed and implemented correctly. Code review, inspection, and testing are three common techniques that can be used to perform verification.

### 11. Compare distributed and centralized version control systems.

A version control system is a software tool that is used to manage changes to source code and other files. There are two main types of version control systems: distributed and centralized.

Distributed version control systems (DVCS) are characterized by the fact that they allow developers to work with a local copy of the repository that contains the full history of the project. In a DVCS, developers can commit changes to their local repository and push them to a remote repository when they are ready to share them with others. DVCSs also allow developers to work offline and to merge changes from multiple sources. Some examples of DVCSs include Git and Mercurial.

Centralized version control systems (CVCS) are characterized by the fact that they rely on a central, shared repository that contains the full history of the project. In a CVCS, developers must check out files from the central repository in order to make changes, and must check in their changes when they are ready to share them with others. CVCSs typically require that developers have an active network connection in order to work with the repository. Some examples of CVCSs include Subversion and Perforce.

There are a number of differences between DVCSs and CVCSs, including the way in which they handle branching and merging, the level of control they provide over access to the repository, and the level of flexibility they offer for working offline. In general, DVCSs are seen as being more flexible and adaptable than CVCSs, but may require a slightly steeper learning curve for users who are not familiar with them.

### 12. Explain basic terms used in git: branch, baseline, clone, commit, push, pull, etc.

Git is a popular distributed version control system that is used by developers to manage changes to source code and other files. Here are some basic terms used in Git:

Branch: A branch is a separate line of development in a Git repository. Branches are used to create new features, fix bugs, or experiment with different approaches to development.

Baseline: A baseline is a specific point in the history of a Git repository that serves as a reference point for further development. Baselines are often used to mark the point at which a feature or bug fix is complete, or to mark the point at which a new version of the software is released.

Clone: A clone is a copy of a Git repository that is created on a developer's local machine. Cloning a repository allows a developer to work with a local copy of the repository and to commit and push changes back to the remote repository.

Commit: A commit is a snapshot of the changes made to a Git repository at a specific point in time. Committing changes saves them to the local repository and allows a developer to revert to a previous version if necessary.

Push: Pushing is the process of sending commits from a developer's local repository to a remote repository. Pushing allows changes to be shared with other developers and makes them available for others to use.

Pull: Pulling is the process of retrieving changes from a remote repository and merging them into a local repository. Pulling allows developers to stay up to date with the latest changes made by other members of the team.

Merge: Merging is the process of combining the changes made in two or more branches of a Git repository into a single branch. Merging allows developers to incorporate changes made in different branches into the main line of development.

These are just a few of the basic terms used in Git. Understanding these terms and how they are used is important for working effectively with Git and collaborating with other developers.

### 13. Describe the risk analysis process. Explain the likelihood, impact, and priority. List some top risks.

Risk analysis is the process of identifying, analyzing, and evaluating risks that may impact an organization or project. The goal of risk analysis is to understand the potential risks that an organization or project may face, and to develop strategies for mitigating or managing those risks.

In the risk analysis process, risks are typically evaluated based on their likelihood, impact, and priority.

Likelihood: The likelihood of a risk occurring is a measure of how probable it is that the risk will happen. Risks with a higher likelihood are more likely to occur, while risks with a lower likelihood are less likely to occur.

Impact: The impact of a risk is a measure of the potential consequences of the risk occurring. Risks with a high impact may have significant consequences for an organization or project, while risks with a low impact may have minimal consequences.

Priority: The priority of a risk is a measure of the importance of addressing the risk. Risks with a high likelihood and high impact are typically given a higher priority, while risks with a low likelihood and low impact are given a lower priority.

Some common risks that organizations and projects may face include:

Financial risks: Risks related to financial issues, such as budget overruns, cost overruns, or revenue shortfalls.

Operational risks: Risks related to the day-to-day operations of an organization, such as equipment failures, supply chain disruptions, or data breaches.

Legal risks: Risks related to legal issues, such as lawsuits, regulatory violations, or intellectual property disputes.

Reputational risks: Risks related to the reputation of an organization, such as negative publicity, customer dissatisfaction, or loss of trust.

By identifying and analyzing these and other risks, organizations and projects can develop strategies for mitigating or managing them, and can reduce the likelihood of negative impacts.

### 14. Explain how to write good user stories using the INVEST principle.

User stories are short, informal descriptions of the desired functionality from the perspective of the user. They are used in agile software development to define and prioritize work in a sprint. Writing good user stories is important for ensuring that the development team has a clear understanding of the desired functionality and for ensuring that the resulting software meets the needs of the users.

One way to write good user stories is to follow the INVEST principle. The INVEST principle is an acronym that stands for the following:

I: Independent: User stories should be independent of one another, meaning that they should not depend on the completion of other stories in order to be valuable.

N: Negotiable: User stories should be negotiable, meaning that they should be open to discussion and refinement. This allows the development team to work with the stakeholders to identify the most valuable and feasible stories to work on.

V: Valuable: User stories should be valuable, meaning that they should provide value to the user or the organization.

E: Estimable: User stories should be estimable, meaning that the development team should be able to estimate the amount of work required to complete them.

S: Small: User stories should be small, meaning that they should be broken down into smaller, more manageable chunks of work. This makes it easier to prioritize and plan work in a sprint.

T: Testable: User stories should be testable, meaning that they should be written in such a way that it is clear how they will be tested once they are implemented. This helps to ensure that the resulting software meets the desired specifications.

By following the INVEST principle, organizations can write user stories that are clear, concise, and valuable, and that can be used to guide development efforts in an agile software development process.

Coupling and cohesion are two important concepts in software design that relate to the interdependence and organization of the components in a system.

Cohesion, on the other hand, refers to the degree to which the elements within a single module or component work together to achieve a single, well-defined purpose. In general, it is generally desirable to have low coupling and high cohesion in a system design. Low coupling means that the components of the system are more independent and easier to modify or replace without affecting the rest of the system. High cohesion means that the components of the system are well-organized and focused on a single, well-defined purpose, which makes them easier to understand and maintain.

### 26. Explain commonly used architecture styles such as client-server, p2p, MVC, layered, and tiered. Give an example for each.

There are many different architecture styles that can be used to design a software system. Here are some commonly used styles, along with examples of each:

The client sends requests to the server, which processes the requests and returns the results. An example of a client-server system is a web server that serves web pages to client computers over the internet.

Peer-to-peer (P2P) architecture: In this style, each computer in the system acts as both a client and a server, communicating directly with other computers in the system. Tiered architecture: In this style, the system is divided into tiers, with each tier performing a specific function and communicating with the tiers above and below it. A tiered architecture is similar to a layered architecture, but the tiers may be distributed across different machines or locations. An example of a tiered system is a web application that has a client tier running on the user's computer, a middle tier running on a web server, and a data tier running on a database server.

Possible refactoring techniques include extracting common logic into reusable methods or creating utility classes.

Long methods: This occurs when a method becomes too large and complex, making it hard to understand and maintain. Possible refactoring techniques include breaking the method up into smaller, more focused methods or extracting logic into separate classes.

Large class: This occurs when a class becomes too large and complex, with many methods and responsibilities. Possible refactoring techniques include breaking the class up into smaller, more focused classes or extracting logic into separate classes.

Divergent change: This occurs when a class is being modified for many different reasons, making it hard to understand and maintain. Possible refactoring techniques include identifying common themes among the changes and extracting them into separate classes or methods.

Shotgun surgery: This occurs when a change to one part of the code requires many other, unrelated parts of the code to be changed as well. Possible refactoring techniques include identifying the common theme among the changes and extracting it into a separate class or method.

Feature envy: This occurs when a class is using the methods or data of another class excessively, indicating that the first class may be better suited as a member of the second class. Possible refactoring techniques include moving the methods or data to the first class or creating a new class to contain them.

Switch statements: These can indicate that a class has too many responsibilities or that it is using inheritance in an inappropriate way. Possible refactoring techniques include extracting logic into separate classes or using polymorphism to eliminate the need for the switch statement.

Message chains: This occurs when a class sends a message to another class, which in turn sends a message to yet another class, creating a chain of dependencies. Possible refactoring techniques include refactoring the chain into a more direct dependency or introducing a new class to act as a mediator between the classes.

Middle man: This occurs when a class is acting as a mediator between two other classes, but is not adding any value. Possible refactoring techniques include removing the middle man class and directly connecting the two classes or extracting the value-adding behavior into a separate class.

Comments: Excessive or outdated comments can make the code hard to read and understand. Possible refactoring techniques include updating or removing outdated comments and refactoring the code to make it more self-explanatory.

These bad smells can violate design principles such as the Single Responsibility Principle, which states that a class should have a single, well-defined responsibility, and the Open-Closed Principle, which states that a class should be open for extension but closed for modification. ### 39. Compare white-box testing and black-box testing.

White-box testing and black-box testing are two different approaches to testing software systems.

White-box testing, also known as structural testing or clear-box testing, is a method of testing in which the tester has access to the internal structure and implementation of the system being tested. The tester can use this knowledge to design test cases that exercise specific paths or branches of the code, and to verify that the code is behaving as expected. White-box testing is often used to test the logic and functionality of individual components or modules, and it can be especially useful for uncovering hidden defects or weaknesses in the code.

Black-box testing, on the other hand, is a method of testing in which the tester does not have access to the internal structure or implementation of the system being tested. The tester can only observe the inputs and outputs of the system, and must design test cases based on the requirements and specifications of the system. Black-box testing is often used to test the overall functionality and behavior of the system from the user's perspective, and it can be used to validate that the system is meeting the stated requirements and behaving as expected.

There are pros and cons to both white-box and black-box testing. White-box testing can be more thorough and efficient, as it allows the tester to focus on specific areas of the code and verify that they are working as expected. However, it requires a deeper understanding of the system and its implementation, and it may not always be practical or feasible to test every possible path or branch of the code. Black-box testing, on the other hand, is generally easier to perform and requires less knowledge of the system's internals. However, it is less comprehensive and may not always uncover hidden defects or weaknesses in the code.

In general, it is best to use a combination of both white-box and black-box testing to ensure that a software system is thoroughly tested and working as expected.

### 40. Explain the TDD workflow and the relationships between TDD, refactoring, and regression testing.

Run the test again: Once the code has been written, you will run the test again. This time, the test should pass, since the code now behaves as expected.

Refactor the code: After the test has passed, you may want to refactor the code to make it more readable, maintainable, or efficient. Refactoring is the process of changing the internal structure of the code without changing its behavior.

Regression tests are a set of tests that verify the correctness of the code after changes have been made.

In summary, TDD is a workflow that involves writing tests, writing code to make the tests pass, and then refactoring the code to improve its quality. ### 47. Compare SAST and DAST.

SAST tools can identify a wide range of security issues, including coding errors, configuration errors, and design flaws. One advantage of SAST is that it can be performed early in the development process, allowing vulnerabilities to be identified and addressed before the application is deployed.

DAST, on the other hand, involves testing the application by sending it inputs and observing its behavior. This is done while the application is running, hence the term "dynamic." DAST tools can identify vulnerabilities that may not be detectable through static analysis, such as vulnerabilities caused by user input or interactions with external systems. One advantage of DAST is that it can identify vulnerabilities that may not be present in the source code, but are introduced during runtime.

In summary, SAST and DAST are complementary approaches to security testing that can be used to identify different types of vulnerabilities in software applications. Both approaches have their own advantages and limitations, and it is often advisable to use both SAST and DAST as part of a comprehensive security testing strategy.
