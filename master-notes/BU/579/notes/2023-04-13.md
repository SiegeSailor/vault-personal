# General Classification of Index Tables

Almost all Database uses B+ Tree as the default index data structure.

- Primary Index
- Clustering Index
- Secondary Index

Index file. `<field_name>` is the key:

```
| ------------ | --------------- |
| <field_name> | Block Pointer   |
| ------------ | --------------- |
| ...          | <block_address> |
```

Single-Level Ordered Indexes: Primary Index, Clustering Index, Secondary Index

- Dense Index -> Each Record -> Physical Index (Pointer must change after every update)
- Sparse Index -> Block -> Logical Index (Used if pointer change frequently)

## Primary Index

Built on an ordering key field (in an ordered file), such as `ssn` in `employee`.

May be dense or sparse:

- Dense index has an index entry for every search key value in the data file
- Sparse index has entries for only some search values

Index used for physically ordering of the file.

Tables stored as Disk Blocks, there is a few tuples in one block. For example, `ssn` 1, 5, and 8 tuples are in block 1, and 9, 10, 11 are in block 2, and so on. Index file only stores the key attribute of the **first** tuple of a block as the key, and then we can find the targeted tuple since we know where the block is pointed to.

The first tuple in a block is so called a _Block Anchor_.

Problem: insertion and deletion of records: Move records around and change index values

- Use unordered overflow file
- Use linked list of overflow records

## Clustering Index

Sparse Index. (non-dense index). Index used for physically ordering of the file.

Built on an ordering non-key field, such as `dno` in `employee`. A block pointer pointes to the first block contains the corresponding key. If a block's last tuple have the key, then the DBMS would keep searching the next block.

## Secondary Index

Dense Index.

Built on a key or non-key; file is not ordered by the column. Same with Primary Index, but the tuples in blocks are not sorted, and it uses tuple address instead of block address.

> Chapter 17 Slide 17-12

- Duplicates occur if index is created on a nonkey field
- Column-based storage of relations: Alternative to traditional way of storing relations by row, Offers advantages for read-only queries, Offers additional freedom in index creation
- 80-20 rule: 80 percent of processing accounted for by only 20 percent of queries and transactions
- Hash indexes do not support range queries

## Tree Structure

We usually use binary-search tree for **in-memory** storage. Database is not an in-memory storage, so we expend the concept.

### B+ Tree

For multi-level index.

- A node is always half full

```
| pointer | key | pointer | key | pointer | key |
```

- A tree is always balanced
- All keys are at the leafs
- Some keys are copied in the internal nodes
